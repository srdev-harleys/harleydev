POS Repository schema, column-level ER diagram, and DBML

Six tables under pos_repository_rista_* hold everything pulled from Rista. Three are typed reports (Sale, Sold-Out, Outlet Status); two are small master tables those reports join against (Outlet Master, Item). The registry → repository rename is fully live — module folder, model names, table names, sequences, security xmlids and the config key all match the code below, verified against real production data. This revision also folds in the response-layout work that followed: a proper missing-vs-zero tracking mechanism, stable line IDs across re-pulls, and a new Sales Detail screen.

What changed since the rename: the missing-vs-zero problem, solved

missing_numbers (new on both Sale and Sale Line) records, at upsert time and before any zero-fallback, which numeric fields Rista's response genuinely omitted versus sent as an explicit 0. The stored Float itself always stays a real number (so pivots/sums keep working), but the UI and CSV/XLSX export both blank the cell wherever it's flagged missing — the first time this schema can tell "Rista didn't send this" apart from "Rista sent zero." round_off_amount is back on the header (dropped in 18.0, restored here) using this exact mechanism: every row synced before the restore is honestly marked unknown rather than shown as a fake 0, and only clears once that invoice is re-pulled. Line upserts also changed from delete-and-recreate to match-by-item_number-and-update-in-place, so a line's Odoo id now survives a re-pull.

Why Outlet Master is one table, not three

The original mapping sheet specified one shared POS_Outlet_Master table for Branch, Brand and Source, discriminated by a lookup_type column — that's what's built. Branch rows carry the one extra field (warehouse_id) the other two never populate.

Why real tables, not reference datasets

Reference datasets are file-backed and re-parsed on every lookup — fine for an outbound API call, but they have no stable row identity for a Many2one to point at. Every arrow above needs exactly that. Data volume here (under 500 rows across both master tables) makes "load per fetch" a non-issue either way.

  • branch_id / brand_id / source_id → outlet.master
  • invoice_number unique per partner
  • ~45 scalar fields: amounts, tax, delivery, event timeline
  • status_reason/remarks, item_log_* added 18.0
  • line_ids → sale.line (1:many)

  • sale_id → sale cascade
  • item_id → item
  • item_number unique per sale
  • sku_code, quantity, item-level tax, options, variant

  • branch_id → outlet.master
  • item_id → item
  • event_key hash, unique per partner
  • status_type, event_type (IN/OUT)

  • branch_id → outlet.master
  • unique(partner, branch_code, channel, order_source)
  • status_value live snapshot, not history

  • lookup_type: branch / brand / source
  • unique(partner, lookup_type, code)
  • warehouse_id → stock.warehouse branch rows only
