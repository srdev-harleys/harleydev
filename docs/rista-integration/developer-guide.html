Implementation Reference — Harleys Odoo 19 Enterprise

Rista POS Integration

Harley's retail POS runs on Rista, an external vendor — not Odoo's own Point of Sale app. This module pulls Rista's sales, sold-out and outlet-status reports into Odoo on a schedule, purely for reporting, built on top of Harley's Connect, the generic external-partner API engine also used for Hyperpure.

1. The problem

Harley's stores ring up sales through Rista, a third-party POS/aggregator system — not Odoo. Odoo's own point_of_sale app is installed but has zero rows in every one of its tables; it plays no role here and isn't touched by this integration. The business need is purely reporting: get Rista's order, sold-out and outlet-status data into Odoo, in a form that can be filtered, pivoted and exported, without building or maintaining a second POS system inside Odoo.

2. Architecture: two independent pieces

PartAnswersWhere it lives
Connect (harleys_connect) "How do I authenticate to a partner, paginate a request, run it on a schedule, and log what happened?" — generic, reusable for any external API. connect.partner, connect.endpoint, connect.manager, connect.job, connect.log
POS Repository (harleys_pos_repository) "What does a Rista response mean, and where does it land?" — Rista-specific typed storage and processors. models/pos_rista_*.py, models/processors.py

The dependency is strictly one-way: POS Repository registers its processors with Connect at load time; Connect has no knowledge of POS Repository's models. The exact same split Hyperpure's own integration is built on, sharing the same Connect engine.

3. The pull pipeline

  1. connect.job — one row per Rista endpoint (Sales Page, Sold-Out History, Outlet Status) — fires on a 24-hour interval, fanning out over all 73 branches, with pull_offset_days=2.
  2. connect.manager.run_job() → execute() makes the one HTTP call (signed-JWT auth, pagination), then resolves the response processor via _get_response_processor(endpoint).
  3. That resolver checks the endpoint's own pos_capture + pos_*_projection flags. As of 19.0.3.17.0, an endpoint with pos_capture=True and no typed projection flag set is a hard error — the old fallback, a generic schema-less capture table, was removed entirely.
  4. The matched processor (RistaSalesPageProcessor / RistaSoldOutHistoryProcessor / RistaOutletStatusProcessor) extracts rows and calls that table's own upsert().
  5. upsert() calls pos.repository.rista.outlet.master and pos.repository.rista.item's _sync() classmethods as a side effect — the only place new branch/brand/source/item rows are ever created. There is no separate "sync items" pull.
  6. Rows land in the typed table; the Rista Reports screens read from there directly.
No more "capture first, type later" Removing the generic capture fallback in 19.0.3.17.0 was a deliberate trade: one less table/screen to maintain, in exchange for a real constraint — a brand-new Rista report, or a second POS vendor, now needs a typed projection built before it can be processed at all.

4. Schema: six tables

All six share partner_id → connect.partner (one Rista connection today); omitted from the tables below since it's identical everywhere.

pos_repository_rista_outlet_master — Outlet Mapping / Brand List / Source List

One shared table for three enumerable dimensions, discriminated by lookup_type — matching the vendor's own mapping sheet design, not three separate tables. See §5.

pos_repository_rista_item — Item Mapping

code = Rista's skuCode; name comes from shortName/longName (Sales Page) or itemName (Sold-Out History) and never includes size/variant. See §6.

pos_repository_rista_sale — POS Orders (one row per invoice)

~60 fields, matching the vendor's own POS_Order mapping sheet column-for-column — cross-checked key-for-key against real captured payloads, zero name mismatches found. unique(partner_id, invoice_number).

FieldNotes
source_id / brand_id / branch_idFK → outlet_master.id, one per lookup_type
discount_amount ("Invoice Total Discount")Reads totalDiscountAmount only — deliberately no fallback to the header's own separate raw discountAmount key, a genuinely distinct field confirmed in real payloads
round_off_amountDropped 18.0, restored 19.0.3.19.0 — see §12 for the historical-data caveat
missing_numbersSee §7
status_reason/status_remarks/item_log_*Modeled per the vendor's own contract despite being confirmed absent from every one of 134k+ real orders — a deliberate bet on future use
line_idsO2M → sale_line; upsert is match-by-item_number and update-in-place as of 19.0.3.19.0, not delete-and-recreate — line ids survive a re-pull

pos_repository_rista_sale_line — POS Order Lines / Sales Detail (one row per item)

~40 fields: the item's own data (sku_code, quantity, tax breakdown, KOT number/status/timestamp, options raw JSON, variant) plus ~15 related+stored header fields so this table stands alone for reporting without a join back to the header.

pos_repository_rista_soldout — Sold Out History

Keyed by event_key, a sha256 hash of the endpoint's own configured Identity Fields (branch, SKU, item type, status type, event type, event date) — deliberately broader than the vendor sheet's own unique(Source,Branch,Item,EventDate), so an item going OUT then back IN the same day/SKU is kept as two distinct events, not collapsed.

pos_repository_rista_outlet_status — Outlet Status (live snapshot, not history)

Keyed by (partner_id, branch_code, channel, order_source) — deliberately wider than the sheet's own (Source, Branch, EventDate), since a branch shows a different status per aggregator channel. One current row per key, overwritten on every poll.

Field-name mismatch, already handled The sheet calls this table's status field statusValue; Rista's real live response for this account sends plain status. upsert() reads row.get("status") or row.get("statusValue") to cover both.

5. Outlet Master: one shared table, not three

The mapping sheet specified one shared POS_Outlet_Master table for Branch, Brand and Source, discriminated by a lookup_type column — that's what's built, not three separate tables. Branch rows carry the one extra field (warehouse_id) the other two never populate. 79 rows live: 73 branch, 3 brand, 3 source.

Reference datasets were considered and rejected for this: they're file-backed and re-parsed on every lookup, fine for driving an outbound API call, but they have no stable row identity for a Many2one to point at — every one of the four typed reports needs exactly that for filtering and grouping. Data volume here (under 500 rows total) makes "load per fetch" a non-issue either way.

The Auto-Map button does an exact code-or-name pass against every warehouse; warehouse_code also accepts direct typing or Excel import (bare code, bare name, or Odoo's own "[code] Name" export format), rather than picking warehouse_id from a dropdown one row at a time.

6. Item Mapping: how it's populated, and its one display gap

There is no dedicated "Items" endpoint — Rista never sends a product catalog API. Every row is grown as a side effect of the two report pulls that happen to mention an item: Sales Page (per line item) and Sold-Out History. _sync() makes exactly one free mapping attempt, at row creation only — an exact match on product.default_code — then never touches product_id again, so it can never silently overwrite a mapping (or a deliberate non-mapping) a person already made.

327 items live; 50 mapped (15%). Checked live: none of the unmapped ones are stale or discontinued — every item currently in the table is either actively selling or actively going in/out of stock within the last 2–3 days.

Same-name rows are a display gap, not duplicate junk Rista's shortName/longName never include the size — e.g. two rows both named "Signature Belgium Chocolate Medovik Cake" are genuinely different, actively-selling SKUs for 600 Gm vs 1 Kg. The size lives in a separate variant field, captured only on the Sale Line, never copied onto the Item Mapping row. Not yet fixed — would need _sync() to also capture a representative variant value here.

7. The missing-vs-zero problem

Every numeric field extraction used to be row.get("fieldName") or 0.0 — this collapses "Rista didn't send this field" and "Rista sent exactly 0" into the identical stored value, with no way to tell them apart later.

missing_numbers (Char, on both Sale and Sale Line) fixes this without changing field types or losing the ability to sum/pivot: at upsert time, before any zero-fallback, it records a pipe-delimited list of which numeric field names were genuinely absent this pull (|round_off_amount|unit_price|). The stored Float itself is always a real number. The UI (invisible="'|field|' in missing_numbers") and CSV/XLSX export (_export_rows override in models/sale_line_report.py) both blank the cell specifically where it's flagged — the number never lies, the display honestly shows "we don't know" instead of a fake zero.

9. Walkthrough: following one order end to end

Verified against a real live Sales Page response (invoice MAH/26-27/10022), not a synthetic example — every field below matched exactly, including timezone-converted timestamps.

  1. Rista sends the order with sourceInfo.source: "zomato", branchCode: "MAH", brandName: "Harley's Fine Baking", and an eventLog array of status transitions.
  2. upsert() calls outlet_master._sync() three times (branch, brand, source) and stores the resulting ids on branch_id/brand_id/source_id.
  3. CGST/SGST amounts are read from the order's own taxes array, matched by tax name — not recomputed from a rate.
  4. Each event-timeline field (accepted_time, closed_time, ...) is pulled from the matching eventLog entry by status, converted from Rista's IST timestamps to UTC for storage.
  5. Each line item calls item._sync() and creates/updates a sale_line row, matched by item_number.

10. What was built, then removed

  • pos.registry.pulled.record (generic, schema-less capture table) + GenericCaptureProcessor + the "Response Repository"/"Build Report" screens built on it — removed 19.0.3.17.0.
  • A raw-JSON response layer (response_data Json field + 60 computed display fields reading straight from it) — built as a first attempt at "show exactly what Rista sent, no calculation" for Sales Detail, reverted in favor of missing_numbers before it was ever installed.
  • "Repository Endpoints" — a list screen duplicating Connect's own Endpoints screen (same rows, same permission gate, same config tab) with zero unique data. Removed; its one genuinely unique piece — Prepare Rista Reporting Endpoints, one-click provisioning of the 3 standard GET endpoints + jobs for a new partner — is kept, reachable from Configuration and from a button on Connect's own endpoint form.
  • 10 zombie tables from a pre-Rista module design (pos_registry_sale, _sale_line, _sale_payment, _sale_summary, 4 old wizards, live_api_wizard) — no ir_model entry, no code reference anywhere. Dropped by hand.
  • Custom import wizards — built, then removed once native Odoo list import (plus the warehouse_code/product_default_code smart-resolve columns) was confirmed to already cover the need.

12. Known limitations / open items

  • Sales Page job: intermittent, self-healing failure. Scheduled pull 'Sales Page' has no registered response processor fires roughly once per 30–90 successful runs. Predates this cycle's work by over a week. Not currently losing data — the next tick retries, and pull_offset_days=2 naturally covers small gaps. Root cause not yet found.
  • round_off_amount's historical gap — every row synced before the 19.0.3.19.0 restore has this value permanently lost (the 18.0 drop was a plain column drop, nothing preserved first). Marked |round_off_amount| in missing_numbers rather than defaulted to a fake zero; only clears on re-pull.
  • Real, live API fields captured but not modeled: totalCost/totalMaterialCost/totalSuppliesCost (zero margin/profitability visibility today), tipAmount, overallRefunds, reprintCount/reprintEvents, and several smaller ones — none in the vendor's own mapping sheet, deliberately flagged rather than added.
  • branchState, branchTIN, orderReadyTimestamp — real, consistently-present fields, explicitly deferred rather than added.
  • Item Mapping same-name collisions — see §6; needs variant captured onto the item record.
  • 277 of 327 items unmapped (85%) — none are stale; either awaiting a manual/Auto-Map pass or lack an obvious exact code/name match today.
  • Migrations for this module were deleted entirely (all 12 version folders) once confirmed no environment other than this dev database has ever installed it, and this dev database's own latest_version is already fully caught up. If this module is ever promoted to a real release process, migrations will need reintroducing from that point forward.
