1The two foundational models

Every batch/lot conversation in Odoo ultimately comes down to two models. Everything else — Manufacturing's "Lot/Serial Numbers" screen, Inventory's Physical Inventory count, the Batch column we built — is a view onto these two.

stock.lot
Identity: name, product_id, company_id. Created once. Not scoped to any module — Manufacturing's "Lot/Serial Numbers" menu is just the management screen for this same model.
→
stock.quant
The ledger: (product, lot, location) → quantity, reserved_quantity, available_quantity. This is what "Physical Inventory" writes to, and what every reservation everywhere else reads from.

This is why a lot created from Manufacturing's product screen is "available universally" — there is no per-module copy. stock.lot is global master data; stock.quant is the single ledger every operation type (Manufacturing consumption, Internal Transfer, Receipt, Delivery) checks before it lets you reserve or move anything.

Harleys customization found

models/stock_picking.py — StockLot._check_unique_lot() is overridden to a no-op (return with nothing). Core Odoo normally prevents two lots with the same name on the same product; Harleys has deliberately disabled that check globally. Worth knowing this is intentional and company-wide, not a bug, if duplicate-looking lot names ever show up.

2The reservation engine — one mechanism, every module

There is no separate "Internal Transfer reservation logic" vs "Purchase reservation logic." Every operation type funnels through the same two methods on stock.move:

MethodWhat it doesWhen it runs
_action_assign() Automatic reservation pass. Looks at real stock.quant availability and creates stock.move.line rows — one per distinct (location, lot, package, owner) combination it finds. Confirming/checking availability on any transfer, receipt, or delivery.
_set_lot_ids() Inverse of the lot_ids field. Runs the same quant-based allocation, but triggered by a user manually adding/removing a lot rather than the automatic pass. This is the method our whole Batch/Batch Qty UI sits on top of. Whenever lot_ids is written — i.e. whenever a batch is added or removed through our widget, on any picking type.

This matters for the map below: because the engine is shared, anything that looks "different" between Internal Transfers and Purchase/Sales is not a different reservation algorithm — it's something module-specific layered on top (a view, a picking-type-specific override, or a business rule), which is exactly what section 5 finds.

↓
stock.quant.quantity / available_quantity
Now real. Every reservation anywhere in the system reads from this exact number.
↓
_action_assign() / _set_lot_ids()
Whatever module you're in — Internal Transfer, Receipt, Delivery, MO consumption — this is what actually gets checked and reserved against

This is exactly the flow you described, and it's confirmed against source, not inferred: the lot is an identity created in one place, its quantity is a fact established in a different place (Physical Inventory), and the reservation engine is a third, shared piece that reads both.

4Internal Transfers — the 3-stage flow you described

Sender → virtual location → receiver is a real, standard Odoo mechanism, not something informal — and Harleys has its own code layered directly on top of it.

Sender warehouse
stock.picking, picking_type_code = internal. Batches here are being sent — fetched from real, already-available stock. No "add new batch" needed, only "which of what I have."
→
Transit location
res.company.internal_transit_location_id — a virtual holding point. Standard Odoo "resupply from another warehouse" route (stock_warehouse.py: resupply_wh_ids / resupply_route_ids) auto-generates this leg.
→
Receiver warehouse
A second, chained internal transfer picking. Batches here are being received — recording what actually arrived, from which lot, how much.

harleys_customization/models/stock_picking.py — StockPicking.button_validate()def button_validate(self):

        lambda picking: picking.location_id.usage == 'transit'
    ).ids
    transit_pickings = self.browse(transit_picking_ids)
    normal_pickings = self - transit_pickings
    ...
    if transit_pickings:
        try:
            result = super(StockPicking, transit_pickings).button_validate()
        except AccessError:
            result = super(StockPicking, transit_pickings.with_user(SUPERUSER_ID)).button_validate()

Harleys specifically detects when a picking's source location is the transit location and validates it with elevated access if a normal user hits an AccessError. This tells us the transit leg is a real, deliberately-supported flow at Harleys — and that whoever validates the receiver-side leg may not otherwise have direct write access to the transit location, which this override works around.

Where the Batch/Batch Qty widget fits: both legs are picking_type_code = 'internal', so both already get the full Batch/Batch Qty/icon-Details treatment we built. The sender's leg is where you'd expect to mostly select existing batches (real stock, real availability); the receiver's leg is where you'd expect to mostly confirm/adjust quantities against what physically showed up.

5Purchase Receipts (GRN) — the confirmed bug

This is the one with an actual, verified root cause — not a guess.

Confirmed via source 
harleys_customization/models/stock_picking.py — StockMove._prepare_move_line_vals()def _prepare_move_line_vals(self, quantity=None, reserved_quant=None):
    vals = super(StockMove, self)._prepare_move_line_vals(quantity, reserved_quant)
    # Override quantity to 0 for GRN
    if self.picking_code == 'incoming':
        vals['quantity'] = 0
    return vals

Every time a new stock.move.line is prepared on a Receipt (picking_code == 'incoming'), Harleys forces its quantity to zero, regardless of what the reservation engine calculated. This is almost certainly deliberate — a GRN (Goods Receipt Note) workflow usually wants the receiving clerk to manually confirm what physically arrived, not have the system silently pre-fill a guessed quantity.

Why this breaks batch selection

Core Odoo's own _compute_lot_ids (the method that decides which lots show up as "Batch" tags at all) explicitly excludes zero-quantity lines:

odoo/addons/stock/models/stock_move.py — _compute_lot_ids()domain = [('move_id', 'in', self.ids), ('lot_id', '!=', False), ('quantity', '!=', 0.0)]

Put the two together: the instant you select a batch on a Receipt, its move line gets created with quantity forced to 0 by Harleys' override — and that same zero immediately makes it invisible to lot_ids, since core excludes quantity == 0 lines. The batch you just picked appears to vanish. That is exactly "fetched and visible in the details popup, but I can't select and add it" — it is being added, and then immediately hidden by a filter it now fails.

This also explains "I had to recreate the record" — starting over sidesteps the specific state that triggers this, without actually fixing the underlying conflict between the two rules.

Decision needed, not yet made

Fixing this means picking one of two directions, and it's a real product decision, not just a code fix:

  • Keep quantity forced to 0 on Receipts (preserve the manual-confirm GRN workflow), but make our Batch/Batch Qty widget use move_line_ids directly as the row source for Receipts specifically, instead of lot_ids — so a zero-quantity line still shows a row (with an editable 0 waiting to be filled in), it just doesn't get silently dropped.
  • Or decide the zero-override shouldn't apply when a batch is added interactively through this new UI at all (only when lines are created some other way) — a narrower, more surgical change.

Not implemented yet — this is exactly the kind of thing to decide together before touching it.

6Sales Deliveries — open question, not yet confirmed

Needs verification

The zero-quantity override found above is scoped specifically to self.picking_code == 'incoming' — it does not apply to outgoing (Delivery) pickings. So the exact mechanism that breaks batch selection on Receipts does not, by itself, explain the same symptom on Deliveries if you're seeing it there too.

Worth confirming directly: on a Sales-generated Delivery Order, does selecting a batch also seem to "vanish," the same as on a Receipt — or does it actually work there, and the Purchase side was the only one with the problem? That answer determines whether Deliveries need separate investigation or are already fine now that Batch/Batch Qty extend to outgoing pickings.
